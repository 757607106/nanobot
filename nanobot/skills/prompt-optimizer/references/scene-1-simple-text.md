# 场景1:简单文本处理

本场景适用于单一明确的文本处理任务,如总结、提取、分类、改写等。

## 核心技术

### 1. 明确具体的指令

**原则**: 用具体数字和明确描述代替模糊词

**反模式** ❌:
```
总结这篇文章,要简短
```

**最佳实践** ✅:
```
总结这篇文章,保持在150字以内
```

**常见模糊词 → 具体替代**:
- "简短" → "150字以内"、"3-4个要点"
- "详细" → "800-1000字"、"包含5个以上的要点"
- "简单" → "使用小学生能理解的语言"
- "专业" → "使用行业术语,面向专业读者"

### 2. 清晰的输出格式定义

**原则**: 明确指定输出的结构和格式

**示例**:
```xml
<output_format>
使用3-4个要点,每个要点一句话
格式: • [要点1]
      • [要点2]
      • [要点3]
</output_format>
```

### 3. 正面描述

**原则**: 说"做什么"而不是"不做什么"

**反模式** ❌:
```
不要使用复杂的句子
不要包含不重要的细节
```

**最佳实践** ✅:
```
使用简单明了的句子
聚焦于核心观点和关键数据
```

## Prompt 模板结构

### 基础模板

```xml
<task>
[动词] + [对象] + [具体要求]
示例: 总结以下文章,保持在150字以内
</task>

<input>
[输入数据或说明]
</input>

<output_format>
[具体的输出格式要求]
- 长度: [具体数字]
- 结构: [要点/段落/表格等]
- 重点: [需要突出什么]
</output_format>
```

### 增强模板(含约束)

```xml
<task>
[具体任务描述]
</task>

<input>
[输入数据]
</input>

<output_format>
[输出格式]
</output_format>

<constraints>
[约束条件]
- 必须包含: [X]
- 必须避免: [Y]
- 语言风格: [Z]
</constraints>
```

## 常见子任务及最佳实践

### 总结文本

**关键要素**:
1. 明确总结长度(字数或要点数)
2. 指定保留的信息类型(主要观点/数据/结论)
3. 目标受众(如适用)

**示例 Prompt**:
```xml
<task>
总结以下新闻文章,保持在200字以内
</task>

<input>
[新闻文章内容]
</input>

<output_format>
使用4-5个要点,每个要点一句话
按重要性排序
重点突出: 事件核心、关键数据、影响分析
</output_format>
```

### 信息提取

**关键要素**:
1. 明确要提取的信息类型
2. 指定输出格式(JSON/表格/列表)
3. 处理缺失数据的规则

**示例 Prompt**:
```xml
<task>
从以下文本中提取所有人名、日期和地点
</task>

<input>
[文本内容]
</input>

<output_format>
以JSON格式输出:
{
  "人名": ["张三", "李四"],
  "日期": ["2024-01-15", "2024-02-20"],
  "地点": ["北京", "上海"]
}

如果某类信息不存在,返回空数组[]
</output_format>
```

### 文本分类

**关键要素**:
1. 明确分类标准和类别
2. 提供每个类别的定义或示例
3. 处理模糊情况的规则

**示例 Prompt**:
```xml
<task>
将以下用户评论分类为: 正面、负面、中性
</task>

<definitions>
- 正面: 表达满意、赞扬或推荐
- 负面: 表达不满、批评或投诉
- 中性: 陈述事实或提问,无明显情绪倾向
</definitions>

<input>
[用户评论]
</input>

<output_format>
分类: [正面/负面/中性]
置信度: [高/中/低]
关键依据: [一句话说明分类理由]
</output_format>
```

### 文本改写

**关键要素**:
1. 明确改写的目标(更正式/更简单/更简洁等)
2. 保持的内容类型
3. 长度要求

**示例 Prompt**:
```xml
<task>
将以下口语化文本改写为正式的商业邮件语言
</task>

<requirements>
- 保持所有关键信息和要求
- 使用礼貌、专业的措辞
- 长度与原文相近(±20%)
</requirements>

<input>
[原始文本]
</input>

<output_format>
[改写后的正式文本]
</output_format>
```

## Claude 4.5 特别注意事项

### 1. 精确遵循字数限制

Claude 4.5 会严格遵守字数限制。如果指定"150字",输出会精确控制在150字左右。

**建议**: 给予一定弹性空间
```
保持在150-180字之间
```

### 2. 示例的一致性

Claude 4.5 对示例中的任何细节都会认真对待。

**注意**: 确保示例完全代表期望的输出风格和格式

**错误示例**:
```xml
<examples>
输入: "这个产品很好用"
输出: 正面 (✓满意)  ← 使用了特殊符号

输入: "质量一般"
输出: 中性           ← 没有使用特殊符号
</examples>
```
→ Claude 可能会混淆是否需要使用特殊符号

**正确示例**:
```xml
<examples>
输入: "这个产品很好用"
输出: 正面

输入: "质量一般"
输出: 中性
</examples>
```
→ 格式完全一致

### 3. 输出简洁性

Claude 4.5 默认更简洁。如果需要详细说明,要明确要求。

**如需详细输出**:
```xml
<task>
总结文章并提供详细的理由说明
</task>

<output_format>
总结: [150字]
理由: 详细说明为什么选择这些要点,每个要点的重要性(300字)
</output_format>
```

## 常见陷阱

### 陷阱1: 目标模糊

❌ "帮我处理一下这段文字"
✅ "将这段文字翻译成英文,保持原意"

### 陷阱2: 缺少格式指定

❌ "提取所有日期"
✅ "提取所有日期,以YYYY-MM-DD格式输出,每行一个"

### 陷阱3: 成功标准不清

❌ "总结得好一点"
✅ "总结要突出核心论点、关键数据和结论,每个要点不超过20字"

### 陷阱4: 使用负面限制

❌ "不要太长,不要太复杂"
✅ "保持在150字以内,使用简单直接的语言"

## 质量检查清单

在生成prompt前,确认:

- [ ] 任务动词明确(总结/提取/分类/改写等)
- [ ] 有具体的数字限制(字数、要点数等)
- [ ] 输出格式清晰定义
- [ ] 使用正面描述而非负面
- [ ] 如有示例,格式完全一致
- [ ] 考虑了边界情况(如缺失数据)
- [ ] 输入数据位置明确

## 完整示例

### 示例1: 新闻总结

```xml
<task>
总结以下新闻报道,面向普通读者,保持在180-200字之间
</task>

<input>
[新闻报道全文]
</input>

<focus>
重点突出:
1. 事件核心内容(谁、什么、何时、何地)
2. 关键数据和事实
3. 对公众的影响
</focus>

<output_format>
使用4-5个完整的句子
第一句概括事件核心
后续句子展开关键细节
最后一句说明影响或意义
</output_format>
```

### 示例2: 数据提取

```xml
<task>
从客户反馈中提取产品问题和改进建议
</task>

<input>
[客户反馈文本]
</input>

<extraction_rules>
问题: 明确指出的产品缺陷或不满
建议: 具体的改进意见或功能请求

如果同时包含问题和建议,分别提取
如果只是抱怨但没有具体问题,标注为"情绪表达"
</extraction_rules>

<output_format>
以表格形式输出:
| 类型 | 内容 | 重要性 |
|------|------|--------|
| 问题 | [具体问题描述] | 高/中/低 |
| 建议 | [具体建议内容] | 高/中/低 |
</output_format>
```

### 示例3: 文本分类(多类别)

```xml
<task>
将客户咨询分类到对应的部门
</task>

<categories>
1. 技术支持 - 产品故障、使用问题、技术咨询
2. 销售咨询 - 价格、购买流程、产品对比
3. 售后服务 - 退换货、维修、保修
4. 账户问题 - 登录、密码、账户信息
5. 其他 - 无法明确归类的咨询
</categories>

<input>
[客户咨询内容]
</input>

<output_format>
分类: [类别名称]
置信度: [高(80%+)/中(50-80%)/低(<50%)]
关键词: [导致此分类的关键词,2-3个]
建议处理: [一句话的处理建议]
</output_format>

<edge_cases>
如果咨询涉及多个类别,选择最主要的类别
如果完全无法判断,选择"其他"并说明原因
</edge_cases>
```
